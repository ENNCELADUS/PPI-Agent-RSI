# PPI Agent 自进化实验设计

更新日期：2026-11-02

本文记录当前讨论形成的实验思路，随讨论更新。尚未确定的 Agent 与 PPI Model 联合自进化机制，不在此预设。

## 1. 实验起点

先在公开 PPI 数据集上开展实验。

初始拥有一个已经在该公开数据集提供的训练集上完成预训练的 PPI Model，作为系统演化前的预测器。Agent 与该模型结合，利用逐轮获得的反馈进行后续实验。

## 2. 数据划分

将公开数据集原有的测试集进一步划分为两部分：

| 数据部分 | 用途 |
| --- | --- |
| 演化集（Evolution Set，`D_evo`） | 用于 10 轮实验，逐轮揭示所选候选的结果，为系统自进化提供反馈 |
| 测试集 | 用于检测自进化完成后系统的能力；其标签不用于进化过程 |

演化集名称已确定，具体划分比例尚未确定。

## 3. 实验流程

```text
公开数据集提供的训练集 → 已预训练的初始 PPI Model
                                      ↓
                               Agent + PPI Model
                                      ↓
                        在演化集上进行 10 轮实验
                        选择候选 → 获取反馈 → 演化
                                      ↓
                         在独立测试集上评价最终系统
```

Agent 与 PPI Model 如何结合、反馈如何驱动两者演化，留待后续讨论确定。

## 4. 两类考核结果

1. **10 轮中的 Hit Rate**：考察系统在逐轮选择候选并获取反馈时的命中表现。
2. **独立测试集上的结果**：考察自进化后的系统对未用于进化的数据的预测与筛选能力。

Hit Rate 的具体汇总口径，以及测试集采用的具体指标，后续讨论时再明确。

## 5. 当前进展

目前已有的是 10 轮 Hit Rate 结果，尚无自进化后系统在上述独立测试集上的评估结果。

已有闭环代码运行的是固定 Agent Harness 和固定 PPI Model，能够利用新增实验事实调整下一轮选择，但尚未实现 Harness 或模型的自动更新。因此，现有 10 轮结果作为当前基线，不代表已完成上述自进化实验。

## 7. Agent Harness 的四个改进方向

以下规划尚未实现。第一版采用双层 Memory，固定底层 LLM、PPI Model、工具和主流程，只迭代经验 Memory。其余方向保留为后续讨论方向。

### 7.1 Memory：从实验记录到可修订经验

**当前状态：**保存历史命中和未检出结果，可按蛋白检索；不保存可持续修订的经验，跨轮不传递完整推理过程。

**改进目标：**保留全部实验事实，并形成有依据、有适用范围、可被反例推翻的经验，使下一轮无需从头解读全部历史。

**拟议实现：**

- 保存逐对实验档案：查询前的 Predictor 分数、Agent 分数、不确定性、选择理由、使用证据，以及查询后的结果、条件与质量。
- 单独保存经验：适用对象或条件、建议动作、支持记录、反例、状态、更新时间及对应 Predictor 版本。
- 每轮反馈后，由独立更新会话比较预期与实际结果，提出新增、修订、合并或撤销经验；无需每轮强行产生新规则。
- 检索同时考虑具体蛋白、家族、定位、结构域、结构特征和相似历史案例；返回支持与反对证据，并控制上下文长度。
- 原始事实不被摘要替代；经验保留修改历史。实验未检出不能直接解释为生物学不互作。

**观察效果：**对照仅有事实记录的固定 Harness，比较后续 Hit Rate 与独立测试表现，并检查经验是否被使用、是否重复犯错或形成过度概括。

### 7.2 证据分析流程：学习何时查询、如何综合

**当前状态：**固定 Prompt 建议先看预测排名，再查注释、同源和历史；LLM 自行综合，分析步骤不强制执行。

**改进目标：**依据历史反馈形成适用于不同候选的分析流程，改进证据使用，而非持续增加查询量。

**拟议实现：**

- 保存做决定时实际可见的证据快照或版本引用，区分实验事实、数据库注释、结构预测与模型推断。
- 反馈后分析失误是否涉及分数偏差、证据冲突、错误同源迁移、忽略条件或证据不足；这些只是诊断假设，不直接当作原因。
- 将有效做法写为局部流程建议，例如出现定位冲突时补查条件，或低同源度时降低互作迁移的权重。
- 在固定范围内修改分析指令或检查步骤，记录版本；用开发侧结果决定保留或回退。

**观察效果：**除两类主考核外，检查预测分数与最终分数的差异、错误类型变化、证据覆盖与成本。复杂解释本身不算收益。

### 7.3 候选选择策略：调整开发与探索

**当前状态：**目标是累计命中，LLM 可自由提交候选，但没有显式记录或更新批次策略。

**改进目标：**让系统依据反馈调整选样方式，并分别观察当前命中与学习后泛化；两者可能存在取舍。

**拟议实现：**

- 为候选记录选择原因，例如 Predictor 高分、命中区域扩展、证据支持的低分候选或新区域探索；允许多个原因。
- 记录批次在蛋白、家族、模块和分数区间上的分布，识别收益是否集中。
- 根据前轮反馈提出下一轮策略及预算分配；不预先固定最优探索比例，也不把 LLM 自报不确定性当作可靠采样依据。
- 保持查询总预算一致，和固定分数排序、随机选择及简单反馈扩展比较。
- 在相同反馈实验中冻结选样；开放自主选样后，结果解释为选样与学习的联合效果。

**观察效果：**Hit Rate、覆盖与集中程度，以及相同预算节点系统的独立测试表现。

### 7.4 工具使用策略：提高有效信息获取效率

**当前状态：**工具接口固定，每轮最多 80 次调用；记录调用参数、成功状态、耗时和返回长度。

**改进目标：**减少重复或低价值查询，改善查询顺序、批量组织与停止条件。

**拟议实现：**

- 关联工具返回与候选判断，记录哪些查询提供了新证据、改变了分数或选择；保留可追溯引用。
- 复用已有静态注释和同源结果，按版本缓存；模型更新后失效旧分数及排名缓存。
- 让系统形成查询建议，例如先批量查定位，再对存在争议的候选深入查询。
- 达到信息充分条件时停止补查，将剩余预算用于其他候选；初期只改调用策略，不开放任意修改工具代码。

**观察效果：**在相同调用预算或相近成本下比较两类主考核，并报告调用量、重复率、失败率与延迟。是否改变判断由日志辅助分析，不能仅靠 LLM 自评证明工具有效。

## 8. 第一版 Harness：双层 Memory

当前确定先采用简单的双层设计：案例 Memory 与经验 Memory。此前设想的实验事实直接并入案例层，不另设事实层。

### 8.1 案例 Memory

保存所有已查询 pair 的判断与反馈，包含命中和未检出案例，每轮追加，不以总结替代原始记录。

每条案例先保留以下字段：

| 字段 | 内容 |
| --- | --- |
| 案例 ID、蛋白对、轮次 | 唯一标识及查询时间位置 |
| Predictor 分数与版本 | 查询前模型的判断 |
| Agent 分数 | 查询前 Agent 的判断 |
| 选择理由与证据引用 | 为什么选择该 pair，使用了哪些信息 |
| 实验结果 | Oracle 反馈；区分未检出、未知和实验失败 |
| 条件、质量及结构引用 | 数据可用时附加，结构文件不直接写入 Prompt |

案例通过工具按需检索。具体字段和检索接口在实现时细化，不要求初版引入复杂检索系统。

### 8.2 经验 Memory

保存从案例中总结的可复用判断规律和选择建议。每轮可以新增、修改或删除经验，也可以不更新。

每条经验先保留：

- 经验 ID 与经验内容。
- 适用范围。
- 支持案例 ID。
- 反例 ID。
- 更新时间及对应 Predictor 版本。

初版将简短的经验列表直接放入下一轮 Prompt。更新时必须检查已有经验，避免每轮只追加总结；新反馈可以推翻旧经验。经验是待验证的推断，不是实验事实。

### 8.3 每轮流程

```text
Agent 读取经验 Memory，按需检索案例 Memory
                    ↓
选择 200 对，保存预测、理由和证据引用
                    ↓
Oracle 返回结果
                    ↓
追加本轮案例
                    ↓
LLM 结合新案例与相关历史案例，更新经验 Memory
                    ↓
保存两层 Memory 快照，进入下一轮
```

经验更新使用独立会话，可沿用同一个底层 LLM。初版不修改主 Prompt 模板、工具实现或 Predictor；每轮变化的是新增案例和经验内容。经验修改历史保留在快照中，便于追踪。

### 8.4 评价与测试

对照仅有案例记录的固定 Harness，观察经验迭代是否改善 10 轮 Hit Rate，以及最终独立测试表现。自动生成经验本身不代表系统已提升。

10 轮结束后冻结案例与经验 Memory。独立测试允许检索冻结快照，不接收测试标签，也不根据测试预测继续更新持久化 Memory。

### 8.5 当前决定与实现状态

2026-11-02：确定第一版 Harness 采用“案例 Memory + 经验 Memory”，先研究经验迭代，其余演化方向暂不开放。该方案尚未写入运行代码，现有代码仍使用原有实验事实 Memory。

## 9. 双层 Memory 的工程实现概述（拟议，尚未实现）

### 9.1 现有代码中的接入点

- `src/eval/rounds.py` 的 `run()` 持有 `tested` 和 `memory`，每轮调用 `run_round()`，评价后通过 `feedback()` 产生下一轮可见事实。这里是接入案例构建、经验更新和恢复的主要位置。
- `evaluate()` 目前只把提交中的 `ranking_score` 和 `uncertainty` 复制到结果行；`rationale`、`evidence_ids` 仅留在原始 `agent/submission.json`。构建案例时必须保留这些查询前信息。
- `src/agent/session.py` 的 `run_round()` 构造 `RoundTools` 并渲染 Prompt；`run_session()` 可复用于独立的经验更新会话。
- `src/agent/tools.py` 的 `RoundTools.memory()` 当前只返回轮次、蛋白对和结果；`call()` 的日志只保存参数、状态及返回长度，不保存工具返回正文。
- `src/agent/pi/ppi_tools.ts` 从工具 spec 动态注册接口，因此新增更新提交工具通常无需改动该转发层。

### 9.2 文件职责与改动范围

| 文件 | 拟议改动 |
| --- | --- |
| 新增 `src/agent/memory.py` | 定义案例和经验字段；构建、检索、序列化快照；校验经验引用；生成经验 Prompt 文本。不读取 hidden 或导入 eval |
| 新增 `src/agent/memory_update.py` | 实现经验更新入口：准备输入、调用独立 `run_session()`、取得结构化经验列表，交给 Memory 模块检查 |
| `src/agent/tools.py` | 扩充案例检索；增加 `MemoryUpdateTools` 和 `submit_experiences` spec；更新会话只暴露历史案例检索与经验提交，不开放候选实验查询或 `submit_batch` |
| `src/agent/session.py` | `run_round()` 增加经验输入；将经验作为单独的上下文区块传入；复用 `run_session()`，不复制 RPC 生命周期逻辑 |
| 新增 `src/agent/prompts/memory_update/system.md`、`round.md`、`nudge.md` | 固定经验更新指令：区分事实和推断、检查反例、允许不更新、提交完整的新经验列表 |
| `src/agent/prompts/system.md`、`round.md` | 一次性增加案例和经验的使用说明，以及经验上下文入口；此后模板固定，逐轮只替换内容 |
| `src/eval/rounds.py` | 保留提交证据；从有效结果构建案例，调用更新并保存快照；按阶段恢复，保证下一轮使用上一轮提交完成的 Memory |
| `tests/agent/test_memory.py`（新增） | 案例字段、检索、经验引用和快照读写测试 |
| `tests/agent/test_tools.py`、`test_session.py` | 检索分页、更新工具权限、经验上下文传入及无更新提交测试 |
| `tests/eval/test_rounds.py` | 轮间状态、崩溃恢复、失败回退和无未来反馈泄漏测试 |
| `src/README.md`、`README.md` | 代码落地时同步模块说明和运行方式 |

“工具与主流程固定”指完成上述一次性接入后，不允许 LLM 在运行期间修改模板或工具代码；并非无需修改现有工程。

### 9.3 案例与经验的数据约定

案例使用稳定 ID，如 `r03:A:B`，蛋白对沿用 `src.data.ids.pair()` 的无序规范化。只把有效且得到结果的查询写为实验案例；无效提交仍留在 evaluator 日志中。

案例包含 `case_id`、`a`、`b`、`round`、`predictor_score`、`predictor_version`、`agent_score`、`uncertainty`、`rationale`、`evidence_ids`、`result`、`source`。实验条件、质量和结构引用为可选字段，不捏造缺失信息。`predictor_score` 由程序从本轮固定分数表读取，不能由 LLM 回忆填写；同时保存分数构建版本或校准信息。

经验包含 `experience_id`、`content`、`scope`、`support_case_ids`、`counterexample_case_ids`、`updated_round`、`predictor_version`。LLM 提交完整列表便于初版管理；修改保留原 ID，新经验分配新 ID，删除仅影响当前列表，历史快照仍保留。引用只能指向截至本轮已揭示案例，程序检查字段和引用；这不能证明经验内容正确。

工具返回证据另存 `evidence.jsonl`，按调用 ID 保存正文或可重建的版本引用。保留现有调用统计日志，给案例中的证据引用提供可追溯对象。蛋白结构当前没有对应工具或数据管线，初版仅预留引用字段，不将结构接入视为已完成。

### 9.4 检索与经验注入

- 初版沿用 `memory` 工具名称，扩展为案例返回；保留按蛋白和结果过滤，增加按案例 ID 查询与分页，返回总量和下一页位置，避免整库塞入上下文。
- 经验更新会话直接获得本轮全部有效案例和上一版经验，可通过相同的只读检索查询历史。若未来输入过长，分批处理须显式记录，不静默截断本轮案例。
- 选择会话收到当前有效经验列表，明确标为“可被推翻的历史总结”，并要求用经验 ID 引用使用过的条目。
- 经验数量或文本长度设置固定上限；具体值在实现时确定，更新会话负责合并精简。所有原始案例仍保留。
- 第 1 轮使用空案例和空经验；第 t 轮只读取截至第 t−1 轮完成的快照。

### 9.5 输出目录与恢复

拟沿用 `data/PRING/runs/<name>/r<R>/`，每轮增加：

```text
round03/
  agent/                    # 现有选择会话与 submission.json
    evidence.jsonl          # 新增：可追溯工具证据
  result.json               # 现有 evaluator 结果
  memory_update/            # 独立更新会话、工具日志和提交
  memory/
    new_cases.jsonl         # 本轮新增案例
    experiences.json        # 本轮更新后的完整经验
    state.json              # 父快照、当前轮次、更新状态和版本
```

案例总库由已完成轮次的增量重建；`state.json` 作为该轮 Memory 完成标记，在必要文件写完后原子发布。选择与经验更新分别记录模型、Prompt 版本、用量与错误，更新成本计入总成本。

当前代码只凭 `result.json` 判断轮次完成，因此必须增加“评价已完成但 Memory 未完成”的恢复分支：保留已揭示结果，只继续 Memory 更新，不重新选样或查询 Oracle。已完成的经验更新直接加载，不重复调用 LLM。旧运行缺少必要预测或证据字段时标明缺失，不用当前模型或新总结伪装成历史快照。

更新失败时，先保存错误和尝试记录，有限重试；仍失败则显式记录使用上一版经验继续，本轮案例照常保留。不能把失败产生的半份经验列表作为新状态。实验运行中采用的失败处理规则保持一致。

### 9.6 实现顺序与验证

1. 先完成纯数据层及测试：案例构建、经验引用、检索与快照。
2. 扩充现有 Memory 工具，接入分数和证据记录；验证仅案例模式仍可运行。
3. 增加独立更新会话和经验注入，先用模拟提交测试完整轮间流程与断点恢复。
4. 依赖和真实数据具备后，再做少量轮次 smoke run，核对两个会话的输入、输出、成本和下一轮使用的快照。

本节不改写 `src/eval/pring_test.py`：它目前是无 Predictor、无 Memory 的独立分类路径，不能直接当作演化后系统评估器。最终测试接入冻结双层 Memory 和 Predictor，需要后续单独实现。演化集划分和候选范围限制也独立处理；双层 Memory 接入本身不完成新的数据协议。
